# Canon governance · version 0.1.0

This package is an evidence-grounded **foundation for approval**, not a claim that a finished MMORPG, approved final art library, or measured production-performance target exists. The founder's October 13 directive is authoritative for the fifteen Oaths, premise and boundaries. Its authorization to propose and implement a migration does not approve every newly authored lore detail.

## Authority and field-level inheritance

| Canon status | Meaning | Required evidence |
|---|---|---|
| LOCKED | Explicit founder-established fact | Exact authenticated user directive or later explicit approval |
| RECOVERED | Prior established material recovered and attributable | Source location, original author, inspected content, approval/establishment basis |
| PROPOSED | New design, provisional technical choice or illustrative record | Design-origin source; pending decision identifier |
| UNRESOLVED | Contradiction, missing source, uncertain approval or unknown runtime | Specific missing evidence, owner and resolution gate |
| DEPRECATED | Explicitly superseded material | Superseding decision and retained historical identity |

Status is not a ranking of literary quality. A proposed excellent design remains proposed. A recovered image is evidence of a visual reference; this does not establish that all details are final founder-approved production specifications. User confirmation that references belong to the Aetherion project establishes provenance and intent to use them; it does not prove UVs, rigging, frame timing, texture alpha, topology or gameplay tests.

Documents declare their default status near the beginning. Quoted locked facts and recovered traits identify their sources explicitly; a mixed record uses field-level notes. Where a record contains locked Oath names and a proposed capital, its overall PROPOSED status must not imply the locked name is negotiable. Source implementation is **verified existing behavior**, not automatically approved full-game canon. Never change an existing castable's balance solely to align it with a new narrative.

## Two independent production axes

Canon status and production status must never be collapsed. Production values: Proposed, Referenced, Approved Concept, In Production, Implemented, Validated, Deprecated. Approval values distinguish unreviewed, reference accepted as direction, explicitly approved, rejected and superseded. A rendered concept can be Referenced/RECOVERED while its desired 3D asset remains Proposed/PROPOSED. `Validated` requires recorded target, test method, exact version, result and limitations. A node simulation passing does not validate GPU appearance, network authority or a physical phone.

Migration statuses are separate: VERIFIED, IMPORTED, BLOCKED, MISSING. VERIFIED means the applicable source behavior was executed successfully in the reported test scope; it does not waive untested rendering or hardware gates. If some mandatory applicable behavior was not exercised, retain IMPORTED or BLOCKED and record the partial pass.

## Approval workflow

1. Open a decision with stable ID, source evidence, prior specification and conflicting facts.
2. Produce a proposal with rationale, alternatives, impacts on lore/assets/mechanics/saves/production and reversible test plan.
3. Run schema, referential-integrity and domain checks; attach evidence, never fabricated test results.
4. Obtain founder approval explicitly identifying the affected decision/version. Silence, an unrelated heart reaction, or general permission to work does not approve all canon proposals.
5. Record approval source, date, reviewer and resulting status. Increment version. Preserve prior content in version history.
6. Migrate references through ID aliases only when necessary; do not recycle IDs. Re-run dependent validation and record release notes.

Only the founder can approve changes to the exact fifteen foundational Oaths. Neither a code-derived display label nor prior assistant-generated narrative can silently add a sixteenth element, merge the Tidal realms, or replace approved reference silhouettes.

## Versioning and ownership

Use semantic document/data releases: patch for corrections without meaning changes; minor for additive proposed records; major for approved breaking semantics or schema changes. Each registry has `schema_version`; source snapshot SHA and actual-file hashes make the technical migration reproducible. Narrative dates use a proposed chronology until approved. Geographic positions remain conceptual relative coordinates until an approved world scale exists.

Discipline owners propose; a continuity reviewer checks global meaning; technical QA checks data/runtime evidence; the founder approves canon. One authoritative index links each fact family. Derived dashboards are rebuildable views, not alternate authorities. Do not edit generated coverage numbers manually.

## Conflict precedence

Current explicit founder canon > explicit prior founder-approved design > verified prior user-established conceptual direction > existing implementation for technical facts > attributed assistant proposal. This ordering does not authorize replacing approved art: record the conflict and retain original bytes. Code is authoritative about what currently runs, not about missing lore. If the source runtime has fewer or more than the requested hundred independently identified castables, report the exact discrepancy instead of inventing abilities.

## Access and security

Source recovery is scoped to Aetherion project materials. Do not publish private assistant memory, credentials, unrelated client content or raw unrelated conversation histories. Source locators may point to owner-private ChatGPT/Library material; note access restrictions so a future collaborator does not mistake a link for an available file. The source repository is read-only. All additions belong to the dedicated Aetherion branch; no merge or deployment is authorized by this foundation PR.
