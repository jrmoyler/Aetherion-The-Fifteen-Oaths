# Elemental interaction matrix

Status: PROPOSED implementation design, except explicitly identified user-established foundations. Numerical values are bounded prototype hypotheses, unvalidated by playtests or profiling. These documents do not change imported Ability Matrix behavior.

Sources: SRC-USER-DIRECTIVE; SRC-RECOVERED-LORE; SRC-SYSTEMS-PROPOSAL. The first two establish the fifteen covenants and broad game pillars. SRC-SYSTEMS-PROPOSAL identifies design authorship, not user approval. Source runtime claims cite SRC-ABILITY-MATRIX-4c4a1eb at commit 4c4a1eb6de6b17fba94c6a074d28cb6b9f32d451.

## Contextual, deterministic rules
INTERACTION_RULES.json contains exactly 120 unordered element pairs: 15 self-pairs and 105 cross-pairs. Each record includes directed state effects and an explicit neutral default. This is not a damage-advantage chart. Every context tag is a proposed authored material/device capability; it is not an intrinsic property of an Oath or every actor carrying that element. If either effect lacks interaction_enabled, the material predicate fails, ownership differs without permission, or budgets are exhausted, effects coexist unchanged.

A pair describes permissible design space. It does not grant every source castable an additional mechanic. source_castable_uids starts empty by design; the actual registry owns source identity, and adapters must be proposed and tested individually. In particular a visual light/shadow projection, blood-themed effect or time-themed VFX is not proof it changes morality, memory, health or time.

## Direction-specific gates
The table context column identifies a family, not a shared target predicate. Each JSON directed_effect has its own material tag, source phenomenon tag, finite reservation and capability-scoped from-state. Fire → Frost requires meltable_ice; Frost → Fire requires hot_surface. A common element pair never satisfies either automatically. All 225 directed entries have independent gates. Capability state ready/applied/expired_or_repaired is scoped to the transition_key on that material instance, not a global ready bit. Actual transition handlers remain unimplemented design obligations.

## Resolver contract
1. Accept authority-stamped events containing event id, root id, server tick, actor id, source uid, extension descriptor version, element id, phenomenon tags, integer magnitude units, target/material ids, owner scope, expiry and ancestry.
2. Snapshot candidate material and actor state at the tick boundary. Reject stale versions and protected or unauthorized volumes before collision queries.
3. Sort by server tick, commitment sequence, actor id and event id. Match the unordered pair, then choose its directed entry from the source event. Self-pairs use one entry. No unordered hash iteration or client wall clock affects outcomes.
4. Check all machine predicates and the authored transition's own from-state. Debit a finite interaction/material budget in the same transaction as the state transition. If insufficient, emit a neutral reason; never partly spend.
5. Apply one bounded transition and append an event receipt. Child events inherit root id, scope ceiling and shorter lifetime; they cannot renew the parent or expand ownership.
6. Publish authoritative outcomes and accessible telegraphs. Clients may predict cosmetic feedback but reconcile to the receipt.

Proposed stress-test fixture: depth 2; at most 3 children per transition; at most 13 accepted events per root (1 + 3 + 9); at most 256 candidate evaluations and 64 state transitions per region tick; per-target reaction cooldown 250 ms; derived volume cap 4 meters radius; derived lifetime cap 10 seconds. Values are intentionally bounded hypotheses. A source ability's visual radius is preserved; these caps apply only to proposed new interactions. Reserve a fair per-actor share before a deterministic round-robin remainder. Reject excess extension transitions with a visible capacity reason instead of silently canceling source behavior. Measure overflow frequency before tuning.

Conservation is a game-state rule: no duplicated water parcels, harvest outputs, item identities, charge ledgers or reward transactions. This is not a claim of physical simulation. Prohibited outcomes include unbounded fire spread, permanent terrain writes, unavoidable repeated hard control, duplicate time rewards and compulsory blood costs imposed on another player.

## Required verification
For every pair, generate a no-material neutral test, a matching-context test, both directional tests where applicable, equal-seed replay, owner rejection, expiry recovery and over-budget rejection. Check exactly 120 unique normalized pairs and complete source element set. These are acceptance specifications until a proposed server resolver is implemented. The package validator can prove coverage/schema properties only; it cannot prove combat fairness, physical simulation or runtime effects from JSON.
